# Migration Documentation

## Migration

## Table created

`user_positions`

## Business purpose

Tabel ini menyimpan daftar konteks kerja yang dapat dipilih oleh pengguna untuk melakukan aktivitas di aplikasi SITANGKAS.

Satu pengguna dapat mempunyai satu atau beberapa posisi.

Satu posisi dibentuk oleh kombinasi:

```text
user_id
jabatan_id
instansi_id
unit_kerja_id
```

Contoh:

```text
Pengguna   : Ahmad
Jabatan    : PPTK
Instansi   : BKAD
Unit kerja : Bidang Anggaran
```

---

## Important distinction

### `is_active`

Berarti posisi masih tersedia dan boleh dipilih.

### Posisi yang sedang digunakan

Tidak disimpan sebagai boolean pada tabel ini.

Posisi yang sedang digunakan harus disimpan per session:

```php
session([
    'active_user_position_id' => $position->id,
]);
```

Beberapa posisi milik pengguna yang sama boleh mempunyai `is_active = true` secara bersamaan.

## Core context columns

### `user_id`

Pengguna pemilik posisi.

Relasi:

```text
user_positions.user_id → users.id
```

Delete behavior: `RESTRICT`.

Alasan: pengguna tidak boleh dihapus secara fisik jika masih mempunyai posisi dan histori aktivitas.

### `jabatan_id`

Jabatan atau role bisnis yang digunakan pengguna dalam konteks tersebut.

Relasi:

```text
user_positions.jabatan_id → jabatans.id
```

Delete behavior: `RESTRICT`.

### `instansi_id`

Instansi yang menjadi lingkup posisi.

Kolom ini sengaja dipertahankan untuk kompatibilitas, filter langsung, audit konteks, dan query administrasi.

Konsistensinya dijaga melalui composite foreign key bersama `unit_kerja_id`.

### `unit_kerja_id`

Unit kerja spesifik tempat posisi berlaku.

Composite relation:

```text
user_positions(unit_kerja_id, instansi_id)
    → unit_kerjas(id, instansi_id)
```

Constraint ini memastikan unit kerja benar-benar berada pada instansi yang sama.

## Availability and period columns

### `is_active`

Menentukan apakah posisi masih tersedia untuk dipilih.

Nilai default: `true`.

Jangan gunakan sebagai indikator posisi yang sedang dipakai pada session.

### `started_at`

Tanggal awal posisi mulai berlaku.

`NULL` berarti tidak ada batas awal yang tercatat.

### `ended_at`

Tanggal akhir posisi berlaku.

`NULL` berarti tidak ada batas akhir yang tercatat.

Database menerapkan check constraint:

```text
ended_at IS NULL
OR started_at IS NULL
OR ended_at >= started_at
```

Posisi efektif hanya jika:

```text
is_active = true
AND deleted_at IS NULL
AND (started_at IS NULL OR started_at <= today)
AND (ended_at IS NULL OR ended_at >= today)
```

## Usage preference

### `last_used_at`

Mencatat waktu terakhir posisi digunakan oleh pengguna.

Digunakan untuk memilih posisi default setelah login berikutnya.

Kolom ini tidak menyatakan bahwa posisi sedang digunakan saat ini.

Saat memperbarui `last_used_at`, jangan mengubah `updated_at`, karena `updated_at` harus tetap mewakili perubahan data master posisi.

Contoh update:

```php
DB::table('user_positions')
    ->where('id', $position->id)
    ->update([
        'last_used_at' => now(),
    ]);
```

## Activation audit

### `activated_at`

Waktu posisi diaktifkan.

### `activated_by_user_id`

Aktor yang mengaktifkan posisi.

Relasi ke `users.id`, dengan `nullOnDelete()` agar histori tetap ada jika akun aktor dihapus.

### `deactivated_at`

Waktu posisi dinonaktifkan.

### `deactivated_by_user_id`

Aktor yang menonaktifkan posisi.

### `deactivation_reason`

Alasan administratif penonaktifan, maksimal 500 karakter.

Saat menonaktifkan posisi, isi seluruh data berikut secara konsisten:

```text
is_active = false
deactivated_at
deactivated_by_user_id
deactivation_reason
```

Saat mengaktifkan kembali:

```text
is_active = true
activated_at
activated_by_user_id
deactivated_at = NULL
deactivated_by_user_id = NULL
deactivation_reason = NULL
```

Digunakan bersama `source_system` untuk sinkronisasi idempotent.

Waktu sinkronisasi terakhir dari sistem sumber.

## Record lifecycle audit

### `created_by_user_id`

Aktor yang membuat record.

### `updated_by_user_id`

Aktor terakhir yang mengubah data administratif record.

Jangan mengubah field ini hanya karena `last_used_at` berubah.

### `deleted_by_user_id`

Aktor yang melakukan soft delete.

### `created_at`, `updated_at`

Timestamp Laravel.

### `deleted_at`

Soft delete.

Gunakan soft delete hanya untuk record salah atau duplikat. Untuk posisi yang tidak lagi berlaku, utamakan `is_active = false` agar histori administratif tetap jelas.

## Unique constraint

Constraint:

```text
uq_user_positions_context
```

Kolom:

```text
user_id
jabatan_id
instansi_id
unit_kerja_id
```

Makna:

Satu pengguna hanya boleh mempunyai satu record untuk kombinasi konteks yang sama.

Jika record pernah di-soft-delete dan diperlukan kembali, restore record lama lalu aktifkan kembali.

Jangan membuat record operasional baru dengan kombinasi identik.

Catatan keputusan setelah migration ini dibuat:

- import `dump-keuangan-202609090855.sql` harus mempertahankan seluruh legacy
  `users.id` sebagai `user_positions.id`;
- baseline terbaru memiliki 371 row legacy dengan konteks identik yang perlu
  disimpan sebagai
  alias non-selectable;
- constraint pada migration ini memang menolak alias tersebut;
- migration ini tidak boleh diedit bila sudah dijalankan;
- forward migration canonical/alias terpisah sudah diterapkan pada 2026-09-14
  untuk mendukung alias tanpa melonggarkan keunikan posisi canonical.

Detail keputusan dan blocker berada di
`../99-legacy/LEGACY_USERS_IMPORT_DECISIONS.md`.

## Foreign-key behavior

Master relations menggunakan `restrictOnDelete()`:

- `users`
- `jabatans`
- `unit_kerjas`

Tujuannya menjaga integritas histori.

Audit actor relations menggunakan `nullOnDelete()`:

- `activated_by_user_id`
- `deactivated_by_user_id`
- `created_by_user_id`
- `updated_by_user_id`
- `deleted_by_user_id`

Jika akun aktor dihapus, record posisi tidak ikut hilang.

## Required application rules

AI agent wajib menerapkan aturan berikut:

1. Posisi yang dipilih harus dimiliki pengguna login.
2. Posisi harus `is_active = true`.
3. Posisi tidak boleh soft-delete.
4. Posisi harus berada dalam periode berlaku.
5. `instansi_id` tidak boleh diambil bebas dari request; gunakan nilai record posisi yang sudah tervalidasi.
6. Setiap aktivitas penting harus mencatat `user_position_id` selain `user_id`.
7. Pergantian posisi harus mengganti session, bukan mengubah posisi lain menjadi tidak aktif.
8. Menambah posisi baru tidak boleh menonaktifkan posisi pengguna yang lain secara otomatis.
9. Menghapus jabatan pengguna umumnya berarti menonaktifkan posisi, bukan hard delete.
10. Jangan menyimpan metadata dokumen SK pada tabel ini.

## Recommended model scopes

```php
public function scopeAvailableForUser($query, int $userId)
{
    return $query
        ->where('user_id', $userId)
        ->where('is_active', true)
        ->whereNull('deleted_at')
        ->where(function ($query) {
            $query->whereNull('started_at')
                ->orWhereDate('started_at', '<=', today());
        })
        ->where(function ($query) {
            $query->whereNull('ended_at')
                ->orWhereDate('ended_at', '>=', today());
        });
}
```

## AI agent prohibited assumptions

AI agent must not assume:

- satu user hanya punya satu posisi;
- hanya satu posisi boleh aktif;
- posisi aktif sama dengan posisi yang sedang dipakai;
- `last_used_at` adalah data audit historis lengkap;
- `deleted_at` sama dengan penonaktifan;
- `unit_kerja_id` bebas dipasangkan dengan `instansi_id` apa pun;
- penghapusan user boleh menghapus posisi secara cascade.
